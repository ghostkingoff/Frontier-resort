> **跑测试的小坑**：Godot 把日志写到控制台句柄，`> 文件` 重定向会得到 0 字节的空文件。
> 想抓日志用 `2>&1 | Out-String` 或在 PowerShell 里用 `Start-Process -RedirectStandardOutput`。
> 另外脚本一旦有解析错误（Parse Error），冒烟测试不会失败退出，而是**永远挂着不结束**——

## 五、开发约定（重要）

- 每次改动都跑 `--smoke`（**动到开局配置 / 建筑表就初始模式与完全测试模式各跑一次**）；`--smoke` / `--wake` 一律用独立测试目录——默认 `user://saves_test`，沙箱等写不了 `user://` 的环境自动回落到 `res://.tmp/saves_test`（`.tmp/` 已 gitignore）；**永不读写玩家存档 `user://saves`**；截图工具只读
- **测试结果看 `[smoke] 结果：通过` 这一行**；PowerShell 里把 stderr 并进管道（`2>&1 | ...`）时退出码会显示成 1，别被误导（`2>$null` 才是真实退出码）
- **客流量公式在 `customer_spawner.gd` 的 `target_flow()`**：目标人数 =（知名度系数 × 口碑系数）×（开门店铺 × 2），对账时向上取整（`target_people()`）；只统计未入住度假屋的游客，店铺只数营业中的消费设施。要调节奏先改这里（系数定义在同文件的 `fame_factor()` / `reputation_factor()` / `open_business_count()`）
- 数值尽量放 `data/*.json`，不要藏在代码里
- 涉及存档结构的改动，除新档外还要用旧档读一次验证兼容性（玩家存档槽 1 是 10-07 的旧档，可以直接用来试）
- 64x 倍速是测试档，发布前删除（`GameClock.Speed.X64`、HUD 的 64x 按钮与 KEY_4）
- **写 GDScript 给无类型返回值标注类型**：`var dirty: int = world.litter_near(...)`。
  不标注会直接 `Parse Error: Cannot infer the type`，而脚本加载失败时冒烟测试是「卡住」而不是「报失败」。
  本轮又踩了三次：`load(...).new()`、`runner._find_building()` 这类都推断不出类型
- **子类不要重复声明基类已有的成员**（`world` / `sprite` / `speed` / `_path`…），
  GDScript 会直接报 `The member "world" already exists in parent class`
- **`.uid` 与 `.gd` 必须成对**：删脚本时一起删 `.uid`，否则仓库里留孤儿文件
- **新的走动 NPC 继承 `scripts/actors/actor.gd`**（顾客和保洁工人已经共用它），
  不要再抄一份寻路 / 行走 / 取帧 / 卡住检测
- **建筑出入口不再限定门口**：`door_cell()` 只是首选，外圈一整圈都能进出
  （`Building.perimeter_cells()` / `World.best_entry_cell()`）。写新逻辑时别再把 `door_cell()` 当唯一入口
- **凡是「可能返回哨兵值」的函数都要检查**：`nearest_walkable()` / `nearest_entry_cell()` /
  `best_entry_cell()` 失败时返回 `(-9999, -9999)`，直接拿去算坐标会变成 ±319968，
  表现为刷屏的 `z_index` 越界错误
- **操作设计原则：只用鼠标要能玩完整流程**，键盘一律只做快捷方式。加新功能时顺手给个鼠标入口
  （现有入口见 `docs/开发进度.md` 第 7.3 节）。建造模式右键退出、顶栏「菜单」= 存档/回主菜单
- **截图不是 1:1**：游戏视口 1920×1080，截图输出 1280×720（缩放 0.667）。
  量像素判断布局问题时必须换算，否则会把正常的面板当成被裁切
- **headless 下 `warp_mouse()` 无效**（鼠标固定在 0,0），要测相机位移就得把 `limit_*` 临时放大，
  否则一帧就撞边界、位移被夹掉，会误判成「惯性没生效」
- **相机平移统一走 `_glide` 速度层**（见 `camera_controller.gd` 的 `_process`）：
  输入只改目标速度，实际位移由指数平滑追上去。新增任何平移方式都接到这一层，
  不要直接改 `position`，否则手感会不一致（惯性/起步平滑只在这一层生效）
- **调滑动惯性用衰减率，且距离与衰减率成反比**：总滑行 ≈ 初速 ÷ 衰减率，
  滑行减半就把 `glide_decay_*` 乘 2。测滑行量必须累计「从松手到停住」的位移，
  只测 0.05 秒会被起步冲量主导，看不出衰减变化
- **寻路网格是增量更新的**（`World._astar_dirty_cells`）。新增任何改动「可通行性」的代码
  （铺地、占地、拆楼、新地形）**必须调 `_mark_astar_cell()`**，否则网格过期 → 客人穿墙，
  而且普通玩法测试很难发现。冒烟测试的「寻路网格同步」检查会逐格对比增量与全量重建
- **`AStarGrid2D` 新建时所有点默认可通行**，必须立刻按地图填一遍，不能只置脏
- **改性能之前先量**：`res://tools/perf_probe.tscn` 会打印各操作的毫秒数。
  本轮就靠它发现瓶颈是「全量重建」而不是 AI（客人每帧才 0.04 毫秒）
- **光照是两层结构**：`CanvasModulate`（`daylight.gd` + `data/lighting.json`）只能**整体压暗**，
  局部提亮必须用 `PointLight2D`。想让某块地方变亮就往那加光源，不要试图改 `CanvasModulate`
- **新增光源用 `World.make_rect_light(inner_size, spread, color)`**：给「要均匀照亮的中心矩形」
  和「渐变带宽度」即可。灯光形状是**矩形平顶纹理**（不是径向）——建筑是矩形，
  用径向光会中间亮四角暗，看起来像地板挡光
- **灯光可被建筑数据覆盖**：`light_on_hour` 固定开灯时刻（不写则 20:00~20:45 随机错落）、`light_shape: "circle"` + `light_radius_cells` 改用圆形光（`World.make_circle_light`）、`light_glow_scale` 放大光晕
- **`rotatable` 的建筑可以四向旋转**（现在只有路灯）：朝向 0~3 = 下→左→上→右，**优先用 `sprite.dir_rects` 的四方向素材换帧**（没有时才退回「把贴图旋转 90° 的整数倍」）；灯光随之偏移一格；朝向随建筑存档（`rot`）
- **灯光层次顺序：地板 → 灯光 → 屋顶/外墙**（`building.gd` 的 `_relayer()`）。
  不能依赖添加顺序，`_build_visuals` 会先建外墙。灯挂在 **World 根**并用 `global_position` 定位，
  **不要挂在建筑下面**：建筑 `z_index = position.y`（可达 2000+），
  `PointLight2D` 默认 z 范围装不下它，灯会完全不参与渲染。
  灯自己的 `z_index` 压到 **-4000** 让建筑画在它上面，开屋顶时屋顶才会盖住灯光
- **熄灯时间在 `_build_lights()` 里按栋抽**（`light_off_hour`）：常规店 = 打烊 + 0~0.5 小时随机，
  24:00 打烊 → **24:00~24:30 之间陆续熄灭**（和 20:00~20:45 陆续开灯呼应）；跨夜店（如酒吧 22→4）
  不拖，仍按自己的打烊时间熄。`update_lights()` 里必须换算成 **连续小时**再比较：
  凌晨 `hour += 24`、跨夜熄灯 `off += 24`。直接写 `hour >= 20 and hour < 4` 永远不成立，跨夜店会整晚不亮
- **`z_index` 合法范围是 [-4096, 4096]**，超范围会刷 `Tried to set Z index to an invalid value`
  且**设值失败**（顺序不受控）。别写 -100000 这类值
- **灯的定位**：`cell_center(cell)` 已是建筑左上格的**中心**，
  建筑中心 = `cell_center(cell) + (footprint - 1) * 0.5 * CELL`（曾多算半个占地导致光偏右下）
- **`PointLight2D` 三个坑**：`texture_scale` 是 **float（等比）**不是 `Vector2`（非等比用节点 `scale.y` 补）；
  没有 `centered` 属性（总是以纹理中心为原点）；默认 `range_z_min/range_z_max` 很窄，
  大 z_index 的对象照不到，需要在 `make_rect_light` 里放开（已处理）
- **排查灯光不生效的顺序**：① 先确认纹理已导入（`load()` 不为 null）
  ② 把同一盏灯挂到场景根、位置放到镜头里，看能不能亮 —— 能亮就说明是
  **挂载层级 / z 范围**问题，而不是参数问题
- **做 A/B 对照测量前先比文件哈希**：本轮我的 `--nolight` 对照把两张图拍在了同一帧，
  永远「完全相同」，我据此写下过错误结论。样本没真正处于不同状态时，
  测出来的是「测试坏了」而不是「功能没生效」
- **死代码审计的结果必须人工复核**：脚本计数很容易误报（本轮误报三次：
  漏同文件内部调用、把同名局部变量当函数、漏 `a.b.emit()` 形式）。
  以 grep 出的原文为依据，不要只信计数
- **日志分两档**：启动摘要 / 存档载入正常打印；`[花钱]` 这类高频输出走
  `GameState.verbose_log`（`--verbose` 打开，开发工具默认打开）
- **纯文档图片目录加 `.gdignore`**（如 `docs/截图/`）：否则 Godot 会给每张图生成
  `.import`，而没有任何代码引用它们，纯属仓库垃圾
- **程序生成的新 PNG 必须导入一次**（`godot --headless --path . --import`），
  否则 `load()` 返回 null。`PointLight2D` 缺纹理时会**完全不发光**，
  表现为「代码全对但一点光都没有」
- **开发工具不经过标题界面**：冒烟测试与截图工具是直接实例化 `main.tscn` 的，`pending_mode` 是空的。
  所以任何「新游戏时才生效」的初始化都要能在这种情况下也跑起来（本轮是靠 `--smoke` / `--screenshot` 判定开发工具模式），
  否则会出现「代码明明写了、跑起来却没生效」
- **草稿丢 `.tmp/`**（已 gitignore），工具放 `tools/`，单个工具文件别超过 ~800 行
